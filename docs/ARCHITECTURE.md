# Архитектура Encryption

## Общая схема

```
┌───────────────────────────── УСТРОЙСТВА ─────────────────────────────┐
│  Сайт (браузер)        ПК (Electron)        Android (WebView+Java)    │
│  └── один и тот же клиент: web/index.html + web/js/*                  │
│      • crypto.js  — двойное шифрование (WebCrypto)                    │
│      • api.js     — REST + WebSocket, автообновление токенов          │
│      • store.js   — локальное хранилище (ключи в зашифрованном виде)  │
│      • app.js     — логика мессенджера, call.js — WebRTC              │
│      • demo-server.js — сервер-заглушка в браузере (демо-режим)       │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  HTTP/REST + WebSocket (wss)
                                ▼
┌──────────────────────── СЕРВЕР (45.90.45.92) ───────────────────────┐
│  nginx :80/:443  →  uvicorn/FastAPI :6000 (+:8080 браузер локально)  │
│                                                                     │
│  server/app.py         сайт (статика) + API + WebSocket + уборка TTL │
│  server/routes/auth.py аккаунты, устройства, сессии, восстановление  │
│  server/routes/users.py профили, ключи, бэкап, контакты, звонки      │
│  server/routes/chats.py чаты, группы, участники, инвайты             │
│  server/routes/messages.py сообщения: приём/выдача конвертов         │
│  server/routes/files.py шифрованные файлы с TTL 24 ч, медиа          │
│  server/realtime.py    WebSocket-хаб: presence, typing, звонки       │
│  server/security.py    Argon2id, JWT, rate-limit, device-binding     │
│  server/db.py          SQLite (WAL) + схема                          │
│                                                                     │
│  data/encryption.db  — метаданные и конверты (только шифротекст)     │
│  data/files/<id>/…   — чанки файлов (удаляются через 24 часа)        │
└─────────────────────────────────────────────────────────────────────┘
```

## Почему Python, а не Rust

Для этого проекта важнее была **скорость и предсказуемость разработки** и
**одинаковое криптоядро на всех платформах**. Выбран Python (FastAPI) для сервера
и JavaScript (WebCrypto) для клиентов:

* сервер вообще не выполняет криптографию содержимого — он транспорт и хранилище,
  поэтому «скорость Rust» здесь ничего не даёт; узкое место — сеть и диск;
* FastAPI даёт асинхронный WebSocket, автодокументацию (`/api/docs`) и простую
  интеграцию с SQLite;
* WebCrypto есть в браузере, в Android WebView, в Electron и в Node — поэтому
  **одно ядро шифрования работает на сайте, на ПК и в Android** (RSA-4096-OAEP,
  AES-256-GCM, ECDH, HKDF, ECDSA, PBKDF2 реализованы нативно и быстро);
* Rust имел бы смысл, если бы крипто-операции делал сервер или если нужен нативный
  Android-клиент без WebView — это направление развития (см. `FEATURES.md`).

## Поток отправки сообщения

1. `app.js::sendMessage()` собирает «плейн» `{text, attachment, from, ts}`.
2. `crypto.js::seal()` шифрует его дважды (см. `SECURITY.md`) и подписывает.
3. Конверт уходит в `POST /api/v1/messages`; сервер валидирует форму
   (`l1`, `wrap` с двумя слоями ключа, `sig`) и кладёт в БД как есть.
4. Сервер рассылает событие `message` всем участникам чата через WebSocket и
   ставит квитанцию «доставлено» тем, кто онлайн.
5. Получатель в `handleRealtime()` → `decryptInto()` → `Crypto.open()`:
   пробует слой 2 (RSA), при неудаче — слой 3 (ECDH), проверяет подпись ECDSA.
6. Сообщение попадает в ленту и в локальный кэш (шифрованный AES-ключом,
   производным от пароля устройства).

## Локальное хранилище (store.js)

| Что | Как защищено |
|---|---|
| Личные ключи (JWK RSA/ECDH/ECDSA) | AES-256-GCM, ключ = PBKDF2(пароль) — на диске только шифротекст |
| Кэш расшифрованных сообщений | AES-256-GCM, тот же ключ устройства |
| Токены сессии | localStorage/`SharedPreferences`; access 15 мин, refresh 30 дней с ротацией |
| Привязка «устройство ↔ аккаунт» | `bound_account` + серверная таблица `device_bindings` |
| Фраза восстановления | никогда не сохраняется; хранится только её обёртка и хеш |

## Realtime-протокол (WebSocket `/ws?token=…`)

| Клиент → сервер | Сервер → клиент |
|---|---|
| `ping` | `pong` |
| `typing {chat_id, state}` | `typing` (всем участникам) |
| `read {chat_id, up_to}` | `read` |
| `call.signal {to, call_id, sdp/ice}` | `call.signal` |
| `call.invite {chat_id, call_id, kind}` | `call.invite` |
| `sync` | `presence`, `message`, `message.*`, `chat.*`, `device.revoked` |

## Звонки

* 1:1 и групповые: сигнализация идёт по WebSocket, медиа — WebRTC P2P (DTLS-SRTP).
* ICE: публичные STUN Google по умолчанию; для работы за симметричным NAT нужен
  TURN (`coturn`) — адрес выдаётся в `POST /api/v1/calls` → `ice_servers`.
* Шаринг экрана: `getDisplayMedia`, подмена видеотрека в существующем соединении.

## Уборка и TTL

`server/app.py::purge_loop()` каждые 5 минут:
1. файлы с `expires_at <= now` → удаляются с диска и из БД;
2. сообщения с истекающим TTL → удаляются, участникам уходит `message.deleted`;
3. истёкшие коды привязки устройств, старые записи rate-limit, история звонков > 30 суток.

## Развёртывание

| Компонент | Артефакт |
|---|---|
| Сервер | `server/` + `deploy/install.sh` (systemd + nginx) |
| Сайт | `web/` (отдаётся тем же сервером на `/`) |
| ПК | `dist/desktop/Encryption-1.0.0-win-x64-portable.exe` |
| Android | `dist/android/Encryption-1.0.0.apk` |

Оболочки Electron и Android содержат копию `web/` внутри и грузят её локально:
без сети приложение открывается, показывает демо-режим и позволяет настроить адрес
сервера. Адрес по умолчанию — `http://45.90.45.92` (через nginx; в настройках
можно поставить `http://45.90.45.92:6000` для прямого подключения).
При локальном запуске скриптами сервер слушает ещё и второй порт `8080` — адрес
для браузера на том же компьютере: порт 6000 браузеры блокируют (`ERR_UNSAFE_PORT`).
