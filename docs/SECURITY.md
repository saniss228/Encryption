# Модель безопасности Encryption

## 1. Двойное шифрование: что именно происходит с каждым сообщением

```
                    НА УСТРОЙСТВЕ ОТПРАВИТЕЛЯ (ключи не покидают устройство)
┌──────────────────────────────────────────────────────────────────────────────┐
│ 1. Текст/файл ──► AES-256-GCM ─────────────────────────► ct₁  (СЛОЙ 1)         │
│                    случайный ключ сообщения mk (32 байта), IV 12 байт,       │
│                    AAD = "enc|<chat_id>|<ts>"                                 │
│                                                                              │
│ 2. mk ──► RSA-4096-OAEP-SHA256(публичный ключ получателя) ─► rsa_mk (СЛОЙ 2) │
│           (для каждого получателя — своя обёртка в wrap[user_id])            │
│                                                                              │
│ 3. mk ──► ECDH(эфемерный ключ, IK получателя) → HKDF-SHA256 → AES-256-GCM ──►│
│           dh_mk + eph (СЛОЙ 3, forward secrecy)                              │
│                                                                              │
│ 4. Подпись: ECDSA-P256(ct₁ ‖ chat_id ‖ ts) ──► sig                          │
└──────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
        Конверт в сети и на сервере:  {v, alg, ts, l1:{iv,ct}, wrap:{uid:{rsa,dh,iv,eph}}, sig, signer}
        Открытого текста, ключей и имён файлов на сервере нет ни в каком виде.
                                    │
                                    ▼
                  НА УСТРОЙСТВЕ ПОЛУЧАТЕЛЯ — обратный порядок:
                  сначала пробуем СЛОЙ 2 (RSA-ключом), если он утерян/сменён —
                  СЛОЙ 3 (ECDH). Оба пути дают mk. Затем AES-GCM-расшифровка ct₁
                  и проверка подписи отправителя.
```

**Зачем два слоя, а не один.** Слой 2 (RSA) гарантирует: даже если атакующий в
реальном времени подменит эфемерные ключи «человек посередине», он не сможет
распаковать RSA-конверт, пока не получит приватный ключ с устройства. Слой 3
(ECDH + эфемерный ключ) гарантирует другое: даже если приватный RSA-ключ
когда-нибудь будет извлечён, прошедшие сообщения останутся нечитаемыми, потому
что ключ сообщения доставлялся и по независимому каналу. Оба слоя независимо
выводят один и тот же `mk`, поэтому потеря одного из ключей не ломает переписку.

## 2. Криптографические примитивы

| Задача | Алгоритм | Примечание |
|---|---|---|
| Шифрование содержимого | AES-256-GCM (tag 128 бит) | аутентифицированное шифрование |
| Обёртка ключа сообщения (слой 2) | RSA-4096-OAEP-SHA256 | 4096 бит, публичный ключ на сервере, приватный — только на устройстве |
| Обёртка ключа (слой 3, FS) | ECDH P-256 → HKDF-SHA256 → AES-256-GCM | эфемерный ключ на каждое сообщение |
| Подпись конверта | ECDSA P-256 (SHA-256) | проверяется при каждом открытии |
| Производная ключа пароля | PBKDF2-SHA512 ×310 000 (на устройстве) | пароль не покидает устройство |
| Хеш пароля на сервере | Argon2id (3 итерации, 64 МБ, 2 потока) | в БД только Argon2id-хеш |
| Бэкап ключей | AES-256-GCM, ключ = PBKDF2 от пароля/фразы | сервер хранит только шифротекст |
| Транспорт | TLS 1.2/1.3 (nginx/uvicorn) + WSS | в комплекте nginx-конфиг |
| Медиа звонков | WebRTC: DTLS-SRTP | ключи не проходят через сервер |

## 3. Что видит сервер, а что — нет

**Видит:** шифротекст, идентификаторы пользователей и чатов, время отправки,
размеры, тип сообщения (текст/файл/звонок), имя файла — тоже зашифровано, но
метаданные «сколько файлов и какого размера» видны.

**Не видит и не может получить:** текст сообщений, содержимое и имена файлов,
приватные ключи, ключ сообщения, расшифрованный бэкап ключей, фразу восстановления.

**Метаданные — честный минимум.** Сервер знает, кто с кем общается и когда. Это
плата за маршрутизацию: чтобы доставить конверт получателю, серверу нужно знать
адресата. Вариант «скрыть и это» (система как в Sealed Sender) — в планах.

## 4. Аутентификация и пароли

1. Клиент считает `PBKDF2-SHA512(пароль, salt="encryption:<логин>", 310000)` —
   это `auth_hash`.
2. По сети уходит только `auth_hash`. Перехват трафика не даёт пароль.
3. Сервер складывает `Argon2id(auth_hash)` — даже при полном дампе БД восстановить
   пароль практически невозможно.
4. Любая ошибка входа (нет логина / неверный пароль) даёт один и тот же ответ —
   нельзя перебором выяснить, какие логины существуют.
5. Лимиты: 30 попыток входа в минуту на IP, 10 регистраций, 240 запросов API в минуту.

## 5. Один аккаунт на устройство

* Устройство получает постоянный `device_id` при первом запуске.
* Таблица `device_bindings` жёстко связывает `device_id` ↔ `user_id`.
* Попытка зарегистрировать другой аккаунт на том же устройстве → `409 DEVICE_BOUND`
  с инструкцией (войти в текущий аккаунт / освободить устройство / взять другое).
* «Освободить устройство» → карантин 30 дней (защита от создания ферм аккаунтов),
  после чего устройство свободно.
* В одном аккаунте не больше 4 устройств.

## 6. Файлы и 24 часа

* Файл шифруется на устройстве по чанкам 1 МБ: `IV(12) ‖ AES-256-GCM(ciphertext+tag)`.
* Сервер пишет чанки как есть, ключ файла приходит только получателям в двухслойной обёртке.
* TTL задаётся при создании: `expires_at = created_at + 24 ч`. Фоновая уборка каждые
  5 минут удаляет и запись в БД, и блоки на диске. Просроченный файл отдаёт `410 FILE_EXPIRED`.
* Имя файла хранится в зашифрованном виде (`name_enc`).
* Сообщения с таймером самоуничтожения удаляются так же, «burn after read» живёт 5 секунд
  после прочтения.

## 7. Что делать при инцидентах

| Ситуация | Действия |
|---|---|
| Потерян телефон | Настройки → Устройства → «Отвязать» это устройство; переписка у вас удалённо не стирается — она и так только на устройстве; ключи на сервере не лежат |
| Кажется, что украли доступ | «Тревожная кнопка»: завершает все сессии, стирает бэкап ключей и фразу восстановления |
| Скомпрометирован RSA-ключ | Слой 3 продолжает защищать новые сообщения; сделайте ротацию ключей в настройках |
| Подозрение на MITM | Сравните отпечатки ключей в информации о чате: они должны совпадать у вас и собеседника (значок 🔏 означает, что подпись ECDSA проверена) |
| Утечка сервера | Атакующий получает шифротекст и метаданные, но не переписку и не ключи |

## 8. Границы гарантий (важно понимать)

* Если устройство заражено, ключи в памяти можно извлечь — это ограничение любых E2E-мессенджеров.
* Без фразы восстановления и без другого авторизованного устройства переписку вернуть нельзя — это не баг, а следствие end-to-end модели.
* Пока не настроен HTTPS, трафик защищён только шифрованием самих сообщений (метаданные видны провайдеру). Поставьте TLS — инструкция в `DEPLOY.md`.
* APK подписан самоподписанным ключом (`android/keystore/encryption.keystore`, пароль `encryption`) — для публикации в Google Play замените его на свой и храните отдельно.
* EXE не подписан сертификатом Windows: при первом запуске SmartScreen покажет предупреждение. Для продакшена нужен код-сертификат (EV/OV).
